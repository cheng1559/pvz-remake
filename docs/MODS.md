# Mods and content packs

Every extension is a Mod; a pure resource pack needs no code entry point. Installation, dependencies, priority, enabled state and uninstallation are all handled by the same manager.

## Installing and managing

```text
/mod
```

`/mod` is the only management command and takes no subcommands. In its window, click Import to choose ZIPs; several packages can be chosen at once. Tick a Mod to enable it and use the arrows to set resource priority: the higher in the list, the higher the priority. Dependencies load first; for resources with the same ID the Mod loaded later wins, while a duplicate gameplay definition ID is an error (replacing a whole definition must be written explicitly in `overrides`). `pvz` is the reserved ID of the built-in base package and cannot be imported.

Mods are kept per player: each player has their own installed Mods, versions, enabled states and order, and `/mod` shows and changes only the current player's. A ZIP is stored once by "ID + content hash", so a ZIP with the same content is shared between players; ZIPs that no player references are cleaned up at startup, and deleting a player deletes their Mod records along with the profile. When a new player is created and the current player has Mods installed, the game asks whether to copy them to the new player (the first player simply takes over the Mods installed before). When switching players, if the other player's enabled Mods or versions differ from the ones running, the game offers to restart to switch; cancelling stays with the current player. The old installation records shared by the whole device are discarded on upgrade.

Importing validates the ZIP and writes the compressed file as is into a separate staging area, without overwriting installed Mods; Cancel/ESC discards the draft and deletes the staged files, both for new packages and for updates to existing Mods. An update to an existing Mod keeps its place in the list.

A fatal Mod error during loading or play opens a Game Error dialog. The left button (`Mods`) opens the Mod manager over it. Apply can restart the game with a new selection, and Cancel returns to the error. The right button (`Exit`) uses the platform's quit action. Recovery keeps the last successful save and builds the dialog and manager with artwork from the base package. It reuses a language already loaded into memory, with the base language and fonts available if loading or drawing the translated interface fails. A handler can consume an error after restoring a usable state. Required loads reject on failure, and a stopped server forwards a fatal error to its client. The manager marks the responsible Mod only when its ID is known. Errors caught while registering one Mod follow the existing startup rollback.

After Apply, if anything was imported, uninstalled or enabled, or enabled items were reordered, confirming the restart first shows `Restarting...` and locks the manager window, saves the current level and the list of pending changes, then restarts. Apply itself does not unpack ZIPs or install or delete Mods; during the next startup only the original PopCap logo is shown while dependencies are checked and Mods are installed and uninstalled in the background, after which the game resources load and the title screen opens. If the task fails, the list and the staged ZIPs are kept, the error is logged, and clicking the logo retries; the running code, audio and images keep using the original archive snapshot. Reordering only disabled items is saved directly, with no restart.

ZIP is the only way to install. Web uses IndexedDB; Native uses `mods/` in the app's writable directory. An archive that is corrupt or missing a dependency is disabled and shows an error in the window, and does not prevent the manager window from opening.

The manager window shows `Loading...` first, and the list once reading finishes.

## File definitions

Both sources and ZIPs use `manifest.json` and `content.json` at the root:

```json
{
  "schemaVersion": 1,
  "id": "example",
  "version": "1.0.0",
  "apiVersion": 1,
  "contentHash": "generated-on-pack",
  "dependencies": []
}
```

A pure resource Mod needs only the above. When it needs scripts, add `gameplay` (`nodeModule`, `cocosModule`) or `client` (`module`, optional `bundle`) to the manifest. The source entry points are `src/server/index.ts` and `src/client/index.ts`; the manifest gives the paths of the compiled output.

`content.json` is the single index of gameplay definitions, presentation definitions and resources:

```json
{
  "gameplay": {
    "plants": "assets/gameplay/plants.json",
    "seeds": "assets/gameplay/seeds.json"
  },
  "presentation": {
    "plants": "assets/presentation/plants.json"
  },
  "resources": {
    "sprites": {
      "example:plant": { "file": "assets/sprites/plant.png", "width": 80, "height": 80 }
    },
    "audio": { "example:launch": "assets/audio/launch.mp3" }
  }
}
```

Paths in the definition index are relative to the root `content.json`. `plants.json`, `seeds.json` and the rest are objects from ID to configuration. Every seed must have a `position`, its cell number within its own group: counted across 8 columns from left to right and top to bottom, starting at 0, 48 cells to a page, and no number may be used twice within a group. There are three kinds of group, in this order: the original, each Mod, and hidden seeds. The base game's seeds belong to the original group, which is the seed chooser grid, and their number is the original's plant seed type; only plants at 0–47 may be there (normally 5 rows, 0–39; when any seed at 40–47, the original's upgrade plants, is owned, it becomes 6 rows as in the original's `Has7Rows`, 70 apart with the first row at y=123; 48 is the original's Imitater). Base seeds with `"hidden": true` belong to the hidden group (the Explode-o-nut, the two bowling nuts, the zombie seeds, the grave seed and the crater seed). A Mod's seeds always belong to that Mod's own group, numbered by the Mod itself from 0, so they never clash with the base game or other Mods, and they cannot be marked `hidden`. A Mod's seeds are not in the seed chooser grid: with `/cheatseed` on, the seed chooser and the almanac give each Mod pages of its own after the original pages, in Mod load order, and the hidden seeds' page comes last; otherwise they are offered through `seedChooser.entries`. A number with no seed is left as an empty cell. As with the other definition tables, a Mod can only register seeds in its own namespace; to move a seed of the base game or of another Mod, replace that seed's whole definition with `overrides.seeds`. Configuration is split into files by category. Presentation definitions are as strict as gameplay definitions: each object accepts only its own fields, and an extra, misspelled or moved field (such as `vault` in a zombie presentation) reports `… is not supported`. The particle that follows a plant's shot is written in the plant presentation's `fireParticle: {id, x, y, delayTicks}` (the Fume-shroom's smoke). The presentations of plants, zombies, projectiles, items and grid items can all have a `viewConfig`: an arbitrary JSON object, kept as is, for the view named by `view` (usually one the Mod registers itself) to read and validate; the base game only checks that it is an object. In a level rule's presentation (`rules`), every field except `graveRise` is for that rule's own view to read and validate. The click area of a dropped item is gameplay: the item definition's `clickPadding` and the level's `itemClickPadding`, and the server decides which item was clicked.

Achievements are written in the gameplay definitions' `achievements` table, from ID to `{ titleKey, descriptionKey, icon: { sprite, index } }`; the icon is cell `index` of `sprite` cut into 70×70 cells, 7 to a row. The achievements page and the award page list the base game's first, then each Mod's in turn. Server scripts grant them with `grantAchievement(world, id, announce)` from the host module `server/achievements/achievements`: one the player already has is not granted again; when `announce` is true it is announced in the level at once, otherwise it waits to be listed on the award page after the level. The client hands the profile to the menu API to save. How an achievement is earned is written in its `trigger: { kind, ...settings }`: the game code only sends server events, and the achievement module observes every event and judges it by the trigger type that `kind` names. The base game's trigger types are `pvz:blast` (`plants`, `kills`), `pvz:bowling` (`plants`, `hits`), `pvz:coin-streak` (`items`, `coins`), `pvz:sun-held` (`sun`), `pvz:win-planting` (`boards`, `skipRules`, `only` / `never`) and `pvz:mind-controlled` (`zombies`); see [ACHIEVEMENTS.md](ACHIEVEMENTS.md). A Mod's new achievements can use these types directly; when a new way of judging is needed, register one with `registry.achievementTriggers.register(ownerId, kind, { validate, observe })` (`registry` is the host module `gameplay/registry`, the instance of `server/registry/GameplayRegistry`); `observe` receives the event, the settings and this achievement's state in the level (kept in the save). To make a base achievement count a Mod's plants, change its `trigger` with `overrides`. A level definition with `achievements: false` grants no achievements on that level, which suits test levels.

The store, the almanac and tools are gameplay definition tables too; as with the other tables, a Mod adds entries in its own namespace and changes anyone's with `overrides`. `store` gives store items by item ID: `{ page, place, cost or prices, message or messages, purchase, level?, completed?, requires?, effect?, unlockChallenge? }`. The item ID is also the key of its purchase count in the profile, so items of different Mods never share one. `page` names a page in the `storePages` table (`{ level? }` or `{ completed: true }`, the original's `StoreScreen::IsPageShown`; pages are in registration order, the base game's four first and each Mod's after them in turn), and `place` is which of the page's 8 cells, in two rows, it takes (0–7); a cell of a page holds only one item: a Mod can put items in empty cells of the base pages or register pages of its own. `prices` and `messages` are picked by how many have been bought; `anyPurchases` and `allPurchases` in `requires` name item IDs. `purchase.kind` is `set`, `count`, `stock`, `timestamp`, `plant` (puts a pot of the plant named by `zenGarden.template` in `settings` into the Zen Garden) or `seed` (sells a seed, which may be an upgrade plant that is not installed yet). The whole store must have exactly one item with `effect: "seedSlots"` (the slot count shown is `seedBank`'s `baseSlots` plus one per purchase, up to `maxSlots`): the seed slot upgrade Crazy Dave sells in levels. An item's look is in the presentation definitions' `store` table (by the same ID: `sprite`, `offset`, `highlight`; the "x5" shown when a `stock` item sells several at once comes from `amount` in the gameplay data; without a `sprite` it draws the packet of the seed it sells), and the store screen's timing and Dave's chatter are in the presentation definitions' `storeDialogue`.

The almanac's plant pages are the seed chooser grid (the original's `AlmanacDialog::GetSeedPosition`) and need no entries; the `almanac` table gives the windows of the zombie pages by zombie ID, `{ place, startingLevel, spawnedOnly?, afterAdventure? }`, where `place` is a position counted from 0 with 5 to a row and may not repeat, and every key must be an existing zombie. The ground a plant or zombie stands on in the almanac is in the presentation definitions' `almanac` table, by plant or zombie ID: `ground` is `day`, `night`, `pool`, `nightpool`, `roof` or `ice`, and a plant can add `upgrade: true` (the upgrade plants' packet background); without an entry it stands on day ground.

Tools are in the `tools` table, from ID to `{ kind }`, where `kind` says what the tool does; for now there is only `shovel` (digs up the plant in a cell). A level's `tools` and awards with `kind: "tool"` must name existing tools, and every tool also needs its look in the presentation definitions' `tools`; one missing is a load failure.

Tutorial scripts are server registrations, like level rules: register one with `registry.tutorials.register(ownerId, id, script)` (`TutorialScript` in `server/tutorials`), and a level uses it with `tutorial: id`. Loading checks that every level's `tutorial` is registered; a misspelled or unregistered name fails the load instead of counting as no tutorial; a level without a tutorial leaves `tutorial` out. A script's own steps (`TutorialResource.step`) use its own namespace, such as `example:dig`, and are kept in the save.

A plant's `visual.nameKey` (required) and `visual.tooltipKey` give the text keys of its name and of its seed chooser description; the text goes in the Mod's `pvz:strings` resource. Without `tooltipKey`, the original's `<nameKey>_TOOLTIP` convention applies. A seed packet draws its own plant by default; when `visual.packetPlant` gives another plant's full ID it draws that one (a bowling nut draws the ordinary Wall-nut). The place and size of the plant picture in the packet are in the plant's `packet.placement` (`{ scale, offsetX, offsetY }`, the original's `SeedPacket::DrawSeedPacket` offsets), `seedPackets.defaultPlacement` when it is absent; `packet`'s other fields are the original's `Plant::DrawSeedType` offsets and pose, and `packet.phase` gives the phase the plant is in in the picture (a small Sun-shroom, a lit Potato Mine), the same as off the board when absent (the gameplay animation's `offBoard`).

Every zombie definition must have `wave: { points, weight, firstWave? }`: the original `ZombieDefinition`'s value `mZombieValue`, pick weight `mPickWeight` and earliest wave `mFirstAllowedWave`. The points are both what spawning the zombie costs and what decides its chance of dropping money when it dies (`Zombie::DropLoot`), so a zombie that only appears in listed waves, from graves or through debug commands needs them too; to keep it from being picked at random from the spawn pool, set `weight` to 0. Entries of a level's `zombiePool` can override these values. A zombie without `wave` is an error at load.

All text lives in a single text table merged by key, `pvz:strings`: the base game's layer is the original's text (including level hints; the server sends only the hints' keys) plus the interface text the base game adds (written by hand in `tools/pvz/ui-strings.json` and merged in when pvz-base is generated; its keys must not repeat the original's). A Mod registers its own `pvz:strings` file as a layer among the `json` resources in `content.json`: new keys must carry its own namespace (such as `example:menu`), and any existing key (the base game's or any Mod's) can be rewritten, the later one in enabled priority winning, so a translation pack lists only the entries it changes, and can translate other Mods' text too; a new key that breaks these rules is ignored and reported in the console. Each background music track is one `music` resource with the ID `pvz:<track name>` (such as `pvz:night_moongrains`); the format is in `shared/content/music.ts` (schemaVersion 3: duration, loop points, stems as audio resource IDs, and optionally the original's burst sections). A music Mod registers the track it replaces under the same ID, and the other tracks stay the base game's. Fonts are overridden only by ID, with no "read the base only" special case: hotkey letters use a separate `pvz:hotkey` (the same file as `pvz:houseofterror16`), so a text pack overrides only the latter and hotkeys keep the original glyphs; an HD pack must also register `pvz:hotkey` to redraw it. `ui.text(key)` accepts only a key, with no default; a missing key shows the key name and is reported in the console. A translation pack states its text language in `manifest.json`'s `locale` (such as `zh-CN`; the last enabled Mod that declares a locale wins, en-US by default); the base game provides that value as `ui.locale`, and image assets with text in them choose their version by it (for example the top of the widescreen Mod's achievements page).

A shooter's `shooter.initialDelayTicks` and `shooter.cadenceTicks` both take integer ranges, for example an initial wait of `{ "min": 0, "max": 150 }` and a cadence of `{ "min": 136, "max": 150 }` (the cadence's minimum must be above zero). The server draws the initial wait and every cadence from the level's RNG; the cadence advances even with no target, and the current clock and the RNG state are kept in the save. A fixed interval uses the same `min` and `max`. The `scaredyshroom` kind is a shooter with a `fright` ability as well (the Scaredy-shroom, `Plant::UpdateScaredyShroom`): `{ center, radius, rowRange, lowerTicks, raiseTicks }`. When a hostile zombie's body comes within `radius` of the plant's top-left corner plus `center`, no more than `rowRange` rows away, the plant goes through four states in turn, `calm`, `lowering` (`lowerTicks`), `scared` and `raising` (a `raiseTicks` range); it does not shoot outside `calm`, and once back in `calm` it waits a whole cadence (`cadenceTicks.max`) before shooting; it cannot be written together with a fuse, mine, chomper, grave buster or growth ability. A fuse, `fuse: { ticks, explosion or freeze }`, takes one of the two: `explosion` is the Cherry Bomb's blast and can add `crater: { ticks }`, which leaves a crater lasting `ticks` in the plant's cell after the blast (the Doom-shroom), the crater belonging to the plant's side; `freeze: { ticks, coldTicks, chillTicks, damage, boardTicks }` is the Ice-shroom's freeze: when the fuse burns out it freezes every hostile plant and zombie for a time within the `ticks` range (`coldTicks` for those already chilled or frozen), chills them for `chillTicks`, deals `damage` (through zombies' shields), and the board records the frozen side for `boardTicks`; a nocturnal plant's fuse does not burn while it sleeps, and zombies eat it as usual. Plant and zombie definitions can both have `unchillable` and `unfreezable`. A plant can only write `true` (at all times; immunity only in certain states is up to its class, such as a Potato Mine while rising, `PotatoMine.keptFromIce`); a zombie writes `true` or a list of zombie states (such as the pole vaulter's `["airborne"]`). `unchillable` takes no slowing at all (neither the Snow Pea nor the Ice-shroom works on it, so it is never frozen either); `unfreezable` is not frozen by the Ice-shroom, only chilled, and takes no freeze damage. A plant's `mindControl: true` (the Hypno-shroom) brings a hostile zombie that eats it while it is awake, or a hostile plant that bites it in one gulp (that bite does not count as swallowing it), over to its side; a zombie that stops eating and walks on draws its speed again by its own type. A zombie's `scale` is its drawn size (the dancers' 0.8, scaled about the Reanim's (30, 120)); it walks the ground track at that size, its animation faster to match. A zombie's `dance` makes it dance to the board's shared beat (`DANCE_BEAT`: on the first 12 beats it walks on `walk`, on the other beats it stands with its arm up on `raise`), and needs a `raise` clip; when one of a group (a leader and the backup dancers it summoned) is eating or frozen the whole group stands still, and when one is chilled the whole group is slowed. `dance.lead: { moonwalkTicks, backup, troupe, holdTicks, summonTicks, summonBeforeX, riseTicks }` makes a leader: first it moonwalks for `moonwalkTicks` on the `moonwalk` clip (which has an `fps` and a `ground` recorded by direction of travel) at that clip's own pace (a chill does not affect it; one frozen during the moonwalk stands where it is once thawed until the moonwalk ends), then plays `point` (which has an `fps` and a `hold`) to snap its fingers, summoning `backup` (which must be a zombie with a `dance` and no `lead`) to each place `{ row, x }` in `troupe` (row and x relative to the leader, mirrored left to right on the plants' side), the backup dancers rising from the ground within `riseTicks`; after that it holds still for `holdTicks`, and when backup dancers are missing it waits `summonTicks`, then summons again on the arm-raising beat once its x is within `summonBeforeX`. A crater seed is a seed with `"kind": "crater"`, with `craterTicks` for how long its crater lasts. A projectile's range limit, `lifetimeTicks`, is written in the projectile definition to apply to everything that shoots it, or in a plant's `shooter.projectile` to apply only to that plant (such as the Puff-shroom's `{ "id": "pvz:spore", "lifetimeTicks": 75 }`; the Scaredy-shroom shoots the same spore with no range limit).

A zombie presentation's `shadow` can have a `scale` (scaled about the shadow's center; the dancers' 0.8); `held: { x, y, scale }` scales the cached picture held in hand by `scale`, then moves it by (`x`, `y`) (the original's `Plant::DrawSeedType`; the Dancing Zombie's 0.8 and (20, 42)); `portrait` can have a `clip`, whose first frame the almanac's small window draws (`idle` by default, drawn at the zombie's `scale`; the seed packet's `packet.clip` and the held picture are drawn at the Reanim's own size); a part in `drops` can have `behind: true`, to be drawn one layer behind the zombie when it falls (the Dancing Zombie's head), and a `scale`, to enlarge it beyond the effect's and the zombie's size (the backup dancer's head, 1.3125: the original swaps its particle scale from the zombie's 0.8 to 1.05). The presentation of a zombie with a `dance` can have `dance: { music?, spotlight?, rise? }`: `music` is the music played when a leader first snaps its fingers (with no more than 15 zombies on the board), stopped when no leading dancer is left on the board; `spotlight: { floor, floorOffset, beam, beamOffset, scale, colors, colorsFrom, colorTicks, colorStep }` is the leader's spotlight after its first snap, `floor` drawn under it and `beam` over it, its color cycling through `colors` by age; `rise` is how backup dancers rise from the ground, with the same fields as a grave zombie's rise (`depth`, `riseTicks`, `clip`), plus a `particle` and `sounds` for when the rise starts. A zombie presentation can have `steps: { effect, marks: [{ at, x, y }] }`: each time the walk animation reaches `at` (a fraction of the clip's length) it plays `effect` once at the zombie's position plus (`x`, `y`), one layer below the zombie, mirrored when it walks right (the Football Zombie's dust). A plant presentation can have `shake: { clip, tracks }`: while the body plays `clip`, every track in `tracks` is offset at random in each direction every tick, by no more than its value (the Doom-shroom's head shaking while its fuse burns). A plant presentation can have `muzzle: { effect, x, y }`: for every shot it plays `effect` once at the projectile's starting point (the projectile's top-left corner) plus (`x`, `y`), above that row's mower layer, mirrored by the projectile's hitbox for plants on the zombies' side (the muzzle smoke of the Puff-shroom, the Scaredy-shroom and the Snow Pea). A plant presentation's `freeze: { effect, layer }` and `freezeSounds` are the effect and sounds played at the plant's center when a freeze fuse goes off (the Ice-shroom). The presentation definition `iceTrap` is the block of ice under a frozen plant or zombie: two images, `back` (behind) and `front` (in front), the ice shard particle `release`, and `{ x, y, scale?, releaseAt }` for each of `zombie` and `plant` (the original's Y-down pixels from the entity's top-left corner); a plant's or zombie's presentation can replace the position of its own group with its own `iceTrap: { x, y, scale? }` (the offsets the original's `Zombie::DrawIceTrap` gives the Pole Vaulting Zombie, the Gargantuar and others).

A projectile presentation can configure a `shadow`: `sprite`, `columns`/`cell` of a single-row atlas, `offset` and `scale`. The shadow is drawn separately on the ground layer, its X following the projectile and its Y the row's start plus `offset.y`, and through the same resource loader it keeps an HD pack's logical size.

Animation owners use a `clips` object keyed by name, including single-clip owners such as items (`idle`), animated projectiles (`fly`), dropped armor (`drop`) and the Whack-a-Zombie rule (`hammer`). Screen scenery uses `screens[screenId].clips` in drawing order. The presentation's top-level `clips` table holds shared effects such as `pvz:sod-roll` and `pvz:final-wave`. Mods can add qualified IDs and override existing entries through `overrides.clips`.

Each clip requires a `reanimId`. Its optional `x` and `y` are local offsets (right and up), and `scale` defaults to 1. A Reanim resource (schemaVersion 3) records its source `fps`. A clip can set an absolute `fps` and multiply it by `rateScale`. Either accepts a number or an ordered pair sampled when playback starts. Clips start at the beginning unless `start` is `random` or `end`. Set `loop` to repeat or `hold` to keep the last pose after one pass. `onlyTracks` selects exact track IDs, `blend` sets transition time in seconds, and `fullLastFrame` includes the last frame for its full interval. For example, an item's spin can use `"clips": {"idle": {"reanimId": "example:coin", "rateScale": [0.6, 1], "loop": true, "start": "random"}}`.

Plant and zombie layers get their time and loop from the server animation and their scale from the view. They accept a single `rateScale` and can attach to another layer with `attachmentTrackId` and an optional `attachmentBase`. Attached layers use the track as their origin. Their own offsets apply when drawn independently. Use the shared `parseClip` or `parseClips` when reading a rule's own configuration, then `prepareClips` and `showClip` to load and play it.

All resource categories share one set of definitions: `sprites`, `fonts`, `audio`, `json`, `text`, `reanim`, `particles`, `music`, `prefabs`. Images use objects; the other categories map an ID to a file path; `audio` supports MP3/WAV. New animation, particle and music configurations use their own categories, and plain JSON uses `json`. Replacing an existing resource only needs its original ID; new gameplay definitions use the Mod's own namespace. A Mod ID is a name without a colon (such as `widescreen`), and it is also the Mod's namespace: the resources and definitions it adds are all written `name:…`, for example `widescreen:background1`. No two Mods have the same ID, so namespaces never overlap; a resource written in another namespace counts as a replacement, not as the Mod's own. The built-in base game's ID is `pvz`. In a sound in presentation configuration (`{ "audio", "foley", "pitchRange"? }`), `audio` is likewise the full audio resource ID, such as `pvz:splat` or `corn:shoop`; an ID without a namespace is an error at validation.

To replace an existing definition whole (the base game's or another Mod's), add `"overrides": "assets/gameplay/overrides.json"` under `gameplay` or `presentation`; the file gives complete definitions grouped by table, for example `{ "plants": { "pvz:peashooter": { ... } } }`. Overrides apply after every Mod has registered, can override any existing ID, and do not depend on load order; an ID can be overridden by only one Mod, otherwise it is a conflict; a target ID that does not exist is an error; an overridden definition has its references checked as usual. Levels can be overridden too, and `levelPatches` apply field by field after the overrides. Overrides replace data only: an entity takes its kind from the overriding definition's `kind`, and an old save whose entity fields do not fit the new definition is handled as an incompatible save.

The presentation definition tables a Mod can add to or override are `plants`, `zombies`, `projectiles`, `gridItems`, `items`, `awards`, `tools`, `foley`, `boards`, `screens`, `levels`, `rules`, `challenges`, `store` and `almanac`, with the same rules as the other definition tables: new IDs only in its own namespace, changes to existing ones through `overrides`. `items` is indexed by dropped item ID, `awards` by level award ID, `rules` by the level rule's `kind`, `store` by store item ID, and `almanac` by the ID of the plant or zombie the almanac shows. Content assembly checks that every plant, zombie, projectile and dropped item in the gameplay definitions has a presentation and that its view is installed, that every tool has a look, and that every level's award has a picture (a seed award uses its plant's presentation, and a `note` also needs `pageImages`); anything missing makes that Mod fail to load, rather than reporting an error only once it appears in a level.

An image can mark a source PNG as premultiplied alpha with `alphaMode: "premultiplied"`; unmarked or `"straight"`, it keeps ordinary RGBA. The mark applies per PNG file, and slices that share a file cannot declare conflicting formats; raw paths read through `assets.sprite(path)` use the same list. The base loader decodes non-interlaced RGBA8 PNGs in one way and restores their colors. Every image (whatever its `alphaMode`, from the base game or a Mod) is "color-filled" when it loads, as in the original: each fully transparent pixel takes the average color of the adjacent visible pixels in the rows above and below, or black when there are none, its alpha unchanged, so that linear sampling does not blend black fringes in at the edges; the RGB that fully transparent pixels carry in the image is therefore not kept. Web and Native use the same path; animations, fades and ordinary Sprites all keep the default blending, and Mods need not set blend factors themselves.

An image's `width` and `height` are its logical size, and `scale` is the texture's resolution multiplier; for example a logical 50×70 that is actually 100×140 is configured with `scale: 2`. The optional `rect`, `offset` and `borders` control cropping, offset and nine-slicing, and `animations` limits the animation IDs a replacement applies to. A font JSON refers to PNGs in the same directory through `layers[].image`, and `textureScale` sets the density of the glyph texture, keeping the original layout.

## Developing and packing

```sh
npm run mod:init -- my-mod
npm run mod:pack -- mods/example
npm run mod:test -- dist/mods/example
```

Besides the base content's sources (`mods/pvz-base/`, its converted assets ignored), the repository tracks only the `mods/example/` sample and `mods/README.md`; other `mods/` subdirectories are for local development and ignored by Git.

The [Mod Lab](../mods/example/README.md) shows gameplay kinds and mixins, Mod data on entities and in saves, level patches, adding and overriding resources, custom views, commands on both sides, menu extensions and lifecycle cleanup. Its capability table points to the actual implementation of each.

Only `mod:pack` compiles. It merges the categorized definitions, collects resources and font atlases, generates the content hash, and outputs `dist/mods/<name>/` with a ZIP beside it; the source directory gets no compiled files. The ZIP's `content.json` keeps the resource mapping, while its `gameplay` and `presentation` point to the generated merged JSON. The installer validates the manifest, modules, file paths, PNG sizes and font atlases.

The loader registers static gameplay definitions, presentation definitions and new resources automatically; the entry point need not register these files again. The entry point is always `register({ host, assets })`, which registers custom plant, zombie and projectile kinds, views or method wrappers through the real host. `host.get(id)` gets any module of its side, the ID being the module's path under `assets/scripts` (without the extension; a directory's `index` by the directory's name), such as `client/plants/PlantView`, `server/seeds/planting` or `shared/protocol`; the client also has `cc` (the engine), `content/definitions` (the definition sources) and `client/views` (the view registries), and the server also has `content/definitions` and `gameplay/registry` (the gameplay registry). A custom plant or zombie view extends `PlantView` or `ZombieView` and is registered with `host.get('client/views').plants.registerView(kind, Class)` (`zombies` for zombies); the presentation definition's `view` then names that kind and its `viewConfig` gives the view's parameters. The base game's zombie view kinds are `zombie` (the default), `flag`, `polevaulter`, `newspaper` and `dancer` (`FlagZombieView`, `PoleVaulterView`, `NewspaperView`, `DancerView`, all extending `ZombieView`); a Mod that replaces these zombies' whole presentation definitions with `overrides` must keep `view`, or they are drawn as ordinary zombies. Both views give subclasses the same members: `onBoard(entity, world)` draws the entity itself on the board every frame (call `super.onBoard` first), `pose` poses the layers (off the board too), `shown(layer, entity)` decides which clip a layer shows, and `playable()` lists the Reanims to load first; available to them are `presentation`, `animation` (the animation definition in the gameplay definitions), `body` (the main body's player), `root` (the node the layers are in; moving it moves the whole picture), `clip(name)`, `ownFrames(reanimId)`, `particle(…)` and `flash`. When a module moves, its ID changes with it. The module lists are generated by `npm run mod:hosts` (`client/content/hostModules.ts`, `server/session/hostModules.ts`) and must be regenerated after a module is added, moved or deleted; the tests check them.

```ts
export function register({ host, assets }) {
    const registry = host.get('gameplay/registry')
    const { Shooter } = host.get('server/plants/Shooter')
    registry.plants.register(assets.id, 'example:rapid_pea', regenerating(Shooter))
}
```

A Mod adds gameplay to plants, zombies and projectiles in only one way: write a kind (a class extending one of the base game's), register it, and select it in definitions with `kind`; the three paragraphs below describe each. A Mod kind's own definition fields and entity fields are named with qualified IDs in the Mod's own namespace (such as `example:regeneration`). Such a field in a definition must be a JSON object and may only be written together with a kind whose static `config` lists it (the same rule as for the base game's `shooter` and similar fields); its contents are checked by the kind's static `validate(definition, id)` when the content loads (`GameplayRegistry.validate`). The entity field of the same name is kept in the save and read back and validated by `restoreOwn`. To add the same gameplay to different kinds, write it as a mixin: a function that takes a base class and returns a subclass of it; the subclass appends its own fields to the static `config`, and `validate`, `restoreOwn` and the methods it overrides all call `super`. A class can stack several mixins, and namespaced fields do not overwrite one another. The example Mod's `regenerating` is used on both a shooter and a zombie. The bowling nut is of the plant kind `bowlingnut`: the values of its `bowling` configuration default to the original's `Plant::UpdateBowling`, and a plant writes only the ones it changes.

Zombies are divided by the gameplay definition's `kind` (`zombie` by default; the base game also has `flag`, `polevaulter`, `newspaper` and `dancer`), which matches the presentation definition's `view` one to one: one class on the server to one view class on the client (`Zombie` and `ZombieView`, `PoleVaulter` and `PoleVaulterView`, …). A custom class extends `Zombie` from `server/zombies/Zombie` or one of the base game's classes (such as `host.get('server/zombies/PoleVaulter').PoleVaulter`) and overrides the methods it changes: for example, when `dodgesBite()` returns `true` a Chomper's bite misses, and when `evades(key)` returns `true` plants targeting with the key `key` (the plant's `targeting.insetKey`, such as the Potato Mine's `pvz:mine`) do not choose it. Register it with `registry.zombies.register(assets.id, kind, Class)`, then write `kind` in the zombie definition. To show the client something of its own, override `snapshotOwn()` to return a JSON object; it appears in the snapshot's `own`, and the client's matching view class reads it with `this.own(zombie, field, validate)`. Each zombie is an instance of its class, in the world's `zombies` list: the instance's fields are saved as they are, so they can only be plain data (refer to another zombie by its entity id); a subclass gives its own fields initial values in its constructor and overrides `restoreOwn(fields, name)` to read them back from the save (taking and validating its own, and passing the rest to `super.restoreOwn`). A class's own definition fields (`vault`, `dance`, `enrage`) may only be written with the class that takes them, and the class's static `config` lists which ones it takes; the pole vaulter's `vault.evades` lists the targeting keys that leave it out while it holds its pole.

Plants are likewise divided by the gameplay definition's `kind` (`plant` by default; the base game also has `shooter`, `scaredyshroom`, `producer`, `sunshroom`, `fuse`, `potatomine`, `chomper`, `gravebuster`, `hypnoshroom`, `wallnut` and `bowlingnut`), which matches the presentation definition's `view` one to one (`Shooter` and `ShooterView`, `Chomper` and `ChomperView`, …). Each plant is an instance of its class, in the world's `plants` list, with an `id` and a `position`, and its fields are saved as they are: a shooter's next shot time `readyAtTick`, a Chomper's stage `phase` and so on are all fields of the class. The state every plant has is `state` (`PLANT_STATES` in `shared/content/plantKinds.ts`): `idle` is on the lawn, and `mowered` has been crushed by a lawn mower and stays in the list until the crush animation finishes; a plant not in play does not count as a plant, and plants in play are taken with `plantsInPlay(world)` / `plantInPlay(world, id)` from `server/level/lawn` (the opposite of the original's `Plant::NotOnGround`). A custom class extends `Plant` from `server/plants/Plant` or one of the base game's classes and overrides the methods it changes: `attack` (shooting), `produce` (producing), `act` (its own ability), `roll` (rolling); when `inedible(world)` returns `true` zombies eating it do it no damage, when `mindControls(world)` returns `true` zombies eating it are mind-controlled, `keptFromCold()` / `keptFromIce()` decide whether it is immune to chilling / freezing at that moment, and `sitOut()` pushes its own timers back on the ticks it is frozen. Register it with `registry.plants.register(assets.id, kind, Class)`, then write `kind` in the plant definition. When it is planted, `start(random, tick)` runs first (drawing the initial wait and other random values); a subclass gives its own fields initial values in its constructor and overrides `restoreOwn` to read them back from the save; what `snapshotOwn(tick?)` returns for the client appears in the snapshot's `own`, and the client view reads it with `this.own(plant, field, validate)`. A class's own definition fields (`shooter`, `fright`, `producer`, `fuse`, `mine`, `chomper`, `graveBuster`, `mindControl`, `bowling`) may only be written with the class that takes them; the animation's `phases`, `offBoard.phase` and `blink.phases` and the presentation definition's `packet.phase` and `shadow.phases` may only name phases its class has (`shared/content/plantKinds.ts`).

Projectiles too are divided by the gameplay definition's `kind` (`projectile` by default; the base game also has `mowing`, a lawn mower once it has set off), which matches the presentation definition's `view` one to one (`Projectile` and `ProjectileView`, `MowingProjectile` and `MowingProjectileView`). Each projectile is an instance of its class, in the world's `projectiles` list, with an `id` and a `position`, and its fields are saved as they are. A custom class extends `Projectile` from `server/projectiles/Projectile` or `MowingProjectile` from `server/projectiles/MowingProjectile` and overrides `canHit` (whether it can hit this target), `strike` (what it does on a hit) and `speedScale` (its speed multiplier this tick); register it with `registry.projectiles.register(assets.id, kind, Class)`, then write `kind` in the projectile definition. The `projectile` kind must have `damage`, and `mowing` must not; a shooter's `shooter.projectile` override also cannot write fields its projectile's kind does not take; a level's `lawnMower` must be of a kind that mows (`MowingProjectile` or a subclass of it). The lawn mower waiting at the end of a row is another class, `Mower` (`server/mowers/Mower.ts`), which on setting off fires a projectile of the level's `lawnMower` type and itself disappears from the row.

The world (`server/state/World`) is a set of lists separated by type: `plants`, `zombies`, `projectiles`, `mowers`, `gridItems`, `items`, each holding the objects themselves by id and iterated in id order, with no ECS components. To keep data of your own on an entity, put it in the entity's `extensions[id]` (a JSON object), where `id` is a qualified ID in your own namespace, registered first with `registry.extensions.register(id, validate?)`: registered data is saved and loaded with the entity and appears in the snapshot's `extensions[id][entityId]`, validated by `validate` and copied every time; unregistered data is neither saved nor sent. A kind's own data is simply written as its fields; `extensions` is for data attached to entities of other kinds. The example Mod's `example:charge` is kept on plants this way.

`ModAssets.json()` reads configuration from the archive. On the client, `assets.sprite(path)` reads one of this Mod's images directly by path, reusing the shared resource decoding and cache, and no other package can replace it; `assets.spriteResource(id)` reads by resource ID, and once the Mod has registered the ID in its own `content.json`, a package of higher priority (such as an HD pack) can replace it under the same ID. Pure resource, data and script Mods use the same loading entry point; a registration failure undoes that Mod's registrations and method wrappers, and skips the Mods that depend on it.

`mod:test` checks the real server registration of a packed directory, without recompiling; given a Mod's source (such as `npm run mod:test -- example`), it first packs it to a temporary directory and checks that pack. It does not replace checking the client or the picture on a real device. After a change, repack, install and restart.

## Changing server rules

Server rules are exported as objects by responsibility, and the first parameter of every function is the game's `session` (with `world`, `definitions`, `gameplayTick` and so on). The host also calls itself through these objects, so a wrapper takes effect on internal calls as well:

| Module | Objects and methods |
| --- | --- |
| `server/seeds/planting` | `planting.seedAvailability`, `rejectSeed`, `selectSeed`, `selectConveyorPacket`, `placePlant`, `createPlant`, `findPlantAt` |
| `server/seeds/tools` | `tools.available`, `select`, `use` |
| `server/items/items` | `items.collect` |
| `server/session/commands` | `commands.execute`, which handles a Mod's own `mod` command |
| `shared/protocol` | Reachable from both sides; the data formats between client and server and their helpers, such as `chooserEntryKey` (a seed chooser card's unique key; the two sides' cards of one seed count as two cards) |
| `server/seeds/seedChooser` | `seedChooser.entries(definitions, owned)` offers cards beyond the base seed chooser grid, by the seeds the player owns (`{ seedId, team? }`, where `team` can move a card to the other side); with `/cheatseed` on, they come after the base game's paged cards, and a duplicate card counts once. These cards count, as owned seeds do, toward the number of slots and toward whether the seed chooser opens (it opens only when there are more cards than slots; otherwise they all go into the seed bank); the chooser snapshot's `entries` lists them, and `chooseSeed` picks one with the same `team`. The client's seed chooser uses `showCards` to decide which cards the grid shows, and calls `onCardHidden` when a card goes back from the seed bank and the grid does not have it. The page-turning buttons are the seed chooser's `pageTurners` (`{ button, step }`); a Mod can redraw them, and turning pages is still handled by the base game |
| `server/session/snapshot` | `snapshot.build`, which adds Mod state to `extensions` |

```ts
const { planting } = host.get('server/seeds/planting')
host.around(planting, 'seedAvailability', function (next, session, seedId, ...rest) {
    const availability = next(session, seedId, ...rest)
    return availability.reason || seedId !== 'my-mod:plant' || ready(session.world)
        ? availability : { reason: 'seed-not-available', warningKey: 'my-mod:not_ready' }
})
```

## Extending CLI commands

Reuse `host.around` to wrap the existing command objects; there is no separate command registration API. Both sides can reach `shared/debug/DebugCli`; parsing, command name completion, parameter hints and static argument value completion all read its `specs.list()`.

For example, a client entry point adding `/example:hello {name}`:

```ts
export function register({ host }) {
    const cli = host.get('shared/debug/DebugCli')
    const spec = { name: 'example:hello', parameters: ['{name}'], minimum: 1 }
    host.around(cli.specs, 'list', next => {
        const entries = next()
        return entries.some(entry => entry.name === spec.name) ? entries : [...entries, spec]
    })

    const { executor } = host.get('platform/debug/DebugCliCommands')
    host.around(executor, 'execute', function (next, input, ...rest) {
        const parsed = cli.parseDebugCliCommand(input)
        if (!('name' in parsed)) return parsed
        if (parsed.name === spec.name) return cli.debugSuccess(`Hello ${parsed.args[0]}`)
        return next(input, ...rest)
    })
}
```

Messages from `debugSuccess` and `debugSyntax` only go to the console, so write the text directly. `debugCondition` means a condition is not met: the debug window closes and the message is shown on screen as advice, so its first argument is a text key and the remaining arguments fill the text's `%s`/`%d` in order (such as `"example:cli_need_level": "Start a playing level first"`, written in the `pvz:strings` text resource the Mod registers; see [File definitions](#file-definitions) above). The client looks it up with `ui.format(key, args)`, translation packs and Mod text can both override it, and the server never needs the text table.

`parameters` gives the hints and the maximum number of arguments, and `minimum` the minimum; the optional `values: { 0: ['a', 'b'] }` provides both validation and completion for the first argument. Names are lowercase and may carry a Mod namespace. Using the existing parser keeps syntax such as quoted arguments.

Commands that change the game state are handled on the server: both sides' entry points apply the same `specs.list` wrapper (which can be moved into a source file the Mod shares between them), the client adds no matching execution wrapper, and the normal entry point forwards the raw command while there is a level. When running integrated, both sides share the syntax object, and the same-name check above keeps completions from appearing twice. A standalone server must declare the syntax too.

The server uses `executor` from `server/debug/debugCommands`: `execute(session, command)` receives the game's `session` (with `world`, `definitions`, `gameplayTick` and so on) and the command as parsed and validated by the server; rules such as planting come from modules such as `server/seeds/planting`, whose first parameter is likewise `session`. For example, to have the server return the message for the command above, keep the syntax wrapper and move the execution wrapper to the server entry point:

```ts
const cli = host.get('shared/debug/DebugCli')
const { executor } = host.get('server/debug/debugCommands')
host.around(executor, 'execute', function (next, session, command) {
    if (command.name === 'example:hello') {
        return cli.debugSuccess(`Hello ${command.args[0]}, tick: ${session.gameplayTick}`)
    }
    return next(session, command)
})
```

Server commands still go through the existing debug permission and command queue, and can run while paused; a Mod checks for itself the world state its operation needs. An execution wrapper handles only its own commands and calls `next` for the others. Syntax is also extended through a wrapper, so the list is never modified directly; when registration fails, the loader undoes the syntax and execution wrappers along with `host.dispose()`, leaving no broken commands or completions behind.

## The base package

The base game's `assets/resources/base.zip` shares `manifest.json`, `content.json`, the definition parsers and the resource parsers with Mods, and no longer has a content index of its own. The base package always loads first and cannot be disabled or uninstalled; its source, `mods/pvz-base/content.json`, indexes categorized JSON as a Mod does, merged into `assets/gameplay.json` and `assets/presentation.json` when packed. The base gameplay also provides `settings` (schemaVersion, the sun and money caps `economy`, the seed bank `seedBank`, the flag waves' `flagWave` and the Zen Garden's `zenGarden`), the full levels, the default text and the seed catalog; Mods loaded later add content in their own namespaces. `npm run mod:pack -- pvz-base` generates `dist/mods/pvz-base.zip` with the generic Mod packer, and `npm run mod:pack -- pvz-base --publish assets/resources/base.zip` publishes the same output to the built-in location; the hash covers the unified index and every file. Every resource (particles included) is registered explicitly in the source `content.json`'s `resources`; packing does not scan for missing ones.

`mod:pack` supports `--publish <zip-file>`: after a successful pack it atomically replaces the given location with the complete ZIP; on failure the previously published file is kept.

## Particle resources

Particles are all registered in `resources.particles`; their JSON uses `schemaVersion: 3`, a fully qualified `id` and `emitters`. Each emitter's `sprite` is a qualified ID too; atlases use `columns`, `rows`, `firstFrame` and `frameCount`. Optional properties override the original's looping, spawn allowance, tint, rotation, collision and fields, and the shared parser fills in the defaults.

Tracks use `{ "nodes": [{ "time": 0, "low": 1, "high": 1 }] }`; `time` is a fraction of the lifetime, and the values of `systemDuration` / `particleDuration` are counted in ticks of 0.01 s. `clipTop`, `clipBottom`, `clipLeft` and `clipRight` (0–1) crop that fraction off each side of the sprite cell as the original's `RenderParticle` does, and the rest is drawn centered on the particle's position plus the unrounded top and left crop amounts (such as the hand reaching out of the ground in the particles of a zombie rising from the ground). An emitter with `fullScreen: true` (the original's `FullScreen`) fills the whole screen with the particle's current color and alpha, wherever the particle is and whatever its size (the original does a `FillRect` over the whole picture; the flashes of the Ice-shroom and the Doom-shroom, whose image is `pvz:whitepixel`); the color and alpha are still computed by the particle kernel, and the client only stretches its quad to the four corners of the screen (`ParticlePlayer`'s `fillScreen`). XML conversion always goes through `tools/pvz/particles.py`: for the base package it unpacks the PAK temporarily, converts straight into `mods/pvz-base/assets/particles/` and registers the files in the resource list, and the generic Mod packer then packs them. The original's curves and random distributions are kept by the conversion and computed by the shared particle kernel.

Scripts play particles with `ParticlePlayer.spawn({ parent, id: 'example:burst', x: 0, y: 0, seed: 123 })`, and every platform uses the same C++ core. `whenReady()` waits for loading; `snapshot()` and `ParticlePlayer.restore()` use the same save structure. The old particle format and old particle saves are no longer accepted; existing Mods' particle resources must be converted and packed again.
